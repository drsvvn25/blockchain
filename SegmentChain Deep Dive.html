SegmentChain, step by step

You do not need to know anything about blockchain to start. Read the five ideas below, play with the small labs, then open any file of your project to see what every field and function does. All numbers and examples come from running your own code.

1A blockchain is a list of records. Each record (a block) holds some transfers and carries a fingerprint of the record before it.
2The fingerprints make cheating visible. Change an old record and every fingerprint after it stops matching.
3Many computers (nodes) keep copies. In a normal blockchain each node stores everything, so the storage each one needs keeps growing.
4Your topic: store only pieces. Cut the history into segments. Each node keeps a few segments plus all the fingerprints, so it can still check what it fetches.
5Your program is a simulator. It pretends to be such a network so you can measure the storage saved and what happens when nodes disappear.
Part 1

Blockchain basics, with things to click

Three ideas are enough: a hash, a block, a chain. Your file blockchain.py implements all three.

1.1 A hash is a fingerprint

A hash function (your code uses SHA-256) turns any text into a fixed 64-character code. The same text always gives the same code. Change one character and the code changes completely. Nobody can work backwards from the code to the text.

1.3 The chain: why tampering shows up

Each block's block_hash includes the previous block's hash. So if block 2 is edited, its hash changes, and block 3 still remembers the old one. The project's verify_chain() walks left to right and reports the first mismatch. Try it below. The lab uses the same rules as your code, with the transaction list reduced to one amount.

Chain lab

Edit an amount, then use the buttons under a block. Stored fingerprints never change on their own, just like a saved ledger.

Try this order. (1) Change block 2's amount: block 2 fails. (2) Press "Recompute my hashes" on block 2: block 2 passes, but block 3 now fails, because it remembers the old hash. (3) Press the big button: everything passes again. The chain was rewritten and nothing noticed. Real blockchains prevent step 3 with mining and agreement between thousands of nodes. Your project has neither, and says so in its limitations.
Part 2

The problem, and your topic's idea

If every node must keep every block, the cost of joining the network only goes up. The segment idea lets a node keep far less and still check what it needs.

Normal blockchain

Every node stores all block data, all headers and the current state. Safe, but each node holds the whole history.

Segment blockchain

History is cut into segments. A node stores the block data of only its segments, plus every header and the state. Each segment is copied onto m nodes.

Three words used everywhere. Header: the small summary of a block (here 160 bytes in the model). State: the latest balances of all accounts (4096 bytes in the model). Block data: the bulky transaction list of a block (1000 bytes in the model). Headers and state are small, so keeping them everywhere is cheap, and they let any node verify a segment it downloads.

The trade-off is the heart of the topic. More replicas make a segment harder to lose but shrink the saving. With your defaults (100 blocks, 5 segments, 30 nodes, 3 replicas) a full node needs 120,096 bytes and the average segmented node 30,096 bytes: 74.9% less.

Part 4

What happens when you press Generate Simulation

The button calls run_simulation() in app.py. These six things happen, in this order. Every later page of the app only reads what was built here.

Read the sidebar. Blocks, transactions per block, seed, segments, nodes, replicas, and the three byte sizes.
Build the chain with Blockchain.generate_chain(blocks, tx_per_block, seed). Output: a list of 100 linked blocks.
Cut it into segments with SegmentationEngine.partition_segments. 100 blocks and 5 segments gives S1 = blocks 0 to 19, S2 = 20 to 39, up to S5 = 80 to 99.
Place replicas with AssignmentEngine.assign_segment_replicas. Each segment lands on 3 different random nodes out of 30.
Prepare the tools. The availability simulator and the integrity checker are created, and the checker saves a copy of the untouched chain.
Compute storage with StorageMetrics. Pages then show charts, run failures, check the probability formula or export files.
Same inputs, same result. The seed is passed to Python's random generator before the chain is built and before replicas are placed, so seed 7 always gives the numbers in this guide. Change the seed and the transfers, timestamps and node choices all change.

Part 6

Failures and odds

Fewer copies of each segment means a risk that every copy sits on a node that is down. Two files measure that risk in two different ways.

Simulated failures (availability.py)

Use the network map in Part 3. At 30% failures (9 nodes), segments S1 and S2 lose all three holders and are gone, so only 3 of 5 segments (60%) remain. S3 and S4 survive on a single node each, which the code calls critical. At 60% failures only S5 survives (20%). One run is a few coin flips, so the results jump in steps of 20 points. Over many random seeds the average at 30% failures is about 98.5% availability, a number I computed by running your logic 200 times.

The paper's formula (probability.py)

The formula P = (A / n)m estimates the chance that a given segment has all its copies on attacker-controlled nodes. Here n is the number of nodes, A how many an attacker controls, and m the copies. Each copy lands on a bad node with chance A/n, and all m copies must do so, so the chances multiply.

Probability lab
-P by the paper's formula
-exact chance (no node picked twice)

The "exact" figure is my own addition for learning. Because a segment's copies are on different nodes, the precise chance is (A/n) × ((A−1)/(n−1)) × … for m terms. For n = 30, A = 3, m = 3 that is 1 in 4,060 against the formula's 1 in 1,000, so the formula is a slightly cautious estimate. Your project uses the paper's formula, and it models a coordinated attacker, which is a different question from the random failures above.

Reference

Glossary

Blockchain
A list of blocks where each block contains the fingerprint of the one before.
Block
One record: some transfers, a time, and links and fingerprints.
Genesis block
The first block (index 0). It has no predecessor, so its previous_hash is 64 zeros.
Hash / SHA-256
A one-way fingerprint function. Same input, same 64 hex characters.
Header
The small summary of a block that is hashed to make its identity.
State
The latest balance of every account after all transfers so far.
Node
One computer that stores data and takes part in the network. Here, a simulated one named N1 to N30.
Segment
A run of consecutive blocks, such as blocks 20 to 39.
Height
The index (position) of a block. A segment spans start_height to end_height.
Replica
One stored copy of a segment on one node. m replicas means m copies.
Checkpoint
A saved copy of all balances at a chosen block, so you need not replay history from the start.
Seed
A number that fixes Python's random choices so a run can be repeated exactly.
Adversary
An attacker assumed to control A nodes, used in the probability formula.
Streamlit
The Python library that turns app.py into the web dashboard.
